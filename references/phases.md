# 阶段流程（A–G）

### 阶段 A：需求与约束
- 明确：站点目的、目标读者、内容类型与数量、更新频率、是否需要评论/统计
- 明确：风格关键词、参考站点、**验收硬标准**
- **需求具象化（从头到尾互动）**：按 `references/requirements-interactive.md`，用 A/B/C +「其他」逐项确认目标、受众、内容量、风格、参考、预算、范围、验收；每轮 ≤3–4 题，未确认项标注待定
- 明确：部署位置（域名/子路径）、预算上限
- **参考同类网站（选择项，必问）**：用 A/B/C +「其他」询问用户是否需要参考同类网站：
  - A. 需要：用搜索引擎/浏览器找 2–3 个同类站，提取结构、栏目、交互与性能做法（**不抄素材与文案**）
  - B. 不需要：按用户描述与风格方向直接做
  - C. 用户提供参考链接：按链接分析
  - 其他：用户自由补充
  结果记录到 `brief.md`；网络不可用时说明情况，由用户决定是否跳过
- 产出：`brief.md`（目标、栏目、风格、约束、非目标）
- **退出**：用户确认 brief；风格方向有 1 张首屏小样确认

### 阶段 B：信息架构与内容模型
- 站点地图：首页 / 列表 / 详情 / 关于 / 统计 / 友链 …
- 内容类型与字段（标题、日期、分类、章节、摘要、标签、封面；字段与默认值见 `references/content-model.md`）
- URL 规则与编号规则（如按分类独立编号）
- 导航层级：一级 + 二级（分类/筛选）；二级可收起、点空白收起
- **退出**：栏目与 URL 表确认；空状态文案确认

### 阶段 B2：技术栈选型与用户确认（动代码前必须完成）

> **GATE（本技能内最高执行门禁，但低于用户明确指令）**
> - **在给出任何技术栈候选或推荐之前，必须先完成环境信息来源确认**（A 自动探测 / B 用户提供）；探测结果是选型的必要输入。
> - 用户明确说"不用查 / 直接推荐 / 跳过"：按用户指令执行，推荐里标注"未探测本机"。
> - 用户拒绝授权：按跳过处理，不擅自扫描。

1. **先选信息来源（A/B/C +「其他」）**：A. 自动探测（推荐，只读一次完成）/ B. 用户自行提供环境信息 / C. 跳过（推荐里标注"未探测本机"）。
   - 自动探测：环境变量与 PATH + 已装程序/服务补充（脚本 `scripts/probe-environment.ps1` 可一次完成）；摘要 ≤20 行
   - 用户提供：让用户按「工具 + 版本」格式给出；直接采用，不重复扫描
   - **结果只列已发现的技术栈与版本号；本地没有的不列、不写"未发现"清单**
   - 摘要写进 `brief.md` 的「环境」小节
2. **参考同类网站的技术栈（条件）**：阶段 A 选 A（需要）→ 自己找 2–3 个风格/主题相似的站点，查看其技术栈（页面源码/meta/公开仓库）；选 C（用户给链接）→ 直接分析用户给的链接；选 B（不需要）→ 跳过此步。记录框架、样式方案、部署方式；另检索当前稳定版本、维护状态与已知问题。
3. **按类别生成候选并逐类确认（禁用固定清单）**：先结合三项输入 ①本机探测结果（已装工具与版本）②阶段 A 的需求与参考站技术栈 ③当前稳定版本与维护状态，为每一类推导 2–3 个候选，再逐类用 A/B/C +「其他」让用户选；每轮 3–4 类。
   类别（按项目取舍）：框架、样式方案、内容方案、字体、图标、交互/动效、部署。
   每个选项必须标注依据：`已装（版本）` / `需新装（体积/时间）` / `参考站使用`；推荐项写明理由。
   **禁止把固定工具名当默认选项**：候选必须来自上面三项输入，需求或环境变化时重新推导；用户可对某类说"按推荐"；全部选完汇总成技术栈表。
   **技术栈不要求必须来自本机**：探测结果是选型的必要输入，但结论不必受限于本机已有工具。若方案需要本机没有的运行时/工具，先说明必要性、下载体积、安装位置与维护代价，用 A/B/C +「其他」询问是否允许下载到项目内（优先项目级依赖，不默认系统级安装）；未获同意不得安装。
4. **询问虚拟环境（技术栈确认后必问）**：用 A/B/C +「其他」询问「是否需要在项目文件夹中创建虚拟环境？」
   - A 需要：说明用途与代价（隔离依赖、占空间、需激活/切换）；Node 项目 → 项目内本地依赖（`node_modules` + 锁定版本）；Python 脚本 → 项目内 `.venv`；两者都有则各自建
   - B 不需要：使用系统/全局已装环境，写清版本要求
   - C 先说明再定：解释区别与影响，等用户决定
   - 记录到 `brief.md`；只在项目内创建，不污染系统环境；未获同意不得创建
5. **落盘**：把探测摘要 + 分项技术栈表 + 虚拟环境选择写进 `brief.md`；用户说"随便"也要讲清推荐理由，不静默拍板。
- **退出**：用户确认分项技术栈与虚拟环境选择；版本已记录；未确认前不进阶段 C

### 阶段 C：工程骨架
- 按确认的技术栈初始化；静态优先
- token 先定，再搭组件；内容用 schema 校验并给默认值；公式按需接 KaTeX
- **子路径部署必做**：`base` + 统一 `url()`（见 `references/scaffold.md`）
- 产出：导航/页脚/列表/详情/404 空壳
- **退出**：构建通过；本地可点通全部路由

### 阶段 D：设计系统
- **美化流程**：先了解用户的美化需求与风格主题（用用户原话）→ 有美化类技能/插件就交给它，本流程作废 → 没有则按用户给的风格/主题检索 2–3 个视觉参考/可运行案例，提炼配色、字体、版式、动效做成风格板，用 A/B/C +「其他」让用户选定，落地后截图验收
- 颜色 token + 亮暗两套；字体 1 标题 + 1 正文（免费可商用），woff2 子集 ≤150KB
- 间距/圆角/阴影变量统一；按钮、卡片、标签、输入框四类基础组件
- **退出**：亮/暗截图对照；390/768/1280 三档正常

### 阶段 E：页面实现（按页推进）
顺序：首页 → 列表 → 详情 → 关于 → 统计/归档/标签 → 404
每页完成：内容真实、亮暗正常、390px 不横向滚动、无开发日志文字
移动端适配与布局改进按 `flows/mobile-adaptation/FLOW.md` 单独执行
- **退出**：全部页面本地可达，console 无报错

### 阶段 F：优化
按 `flows/performance/FLOW.md` 的预算表测量并记录 before/after；未达标不部署
- **退出**：预算达标；Lighthouse 移动端 ≥85

### 阶段 G：验证与部署
按 `flows/qa-launch/FLOW.md` 执行；本地预览 → 用户说"推" → 部署 → 线上验证
- **退出**：关键页 200 且元素存在；用户确认
